# APP-12 일정 공유 기능 MVP 사용자 흐름 정리

## 0. 목적

SHJJ Brief의 회사 일정 공유 기능을 실제 사용자가 한 번에 이해하고 사용할 수 있도록 관리자, 직원, 권한, 초대코드, 일정 등록 흐름을 정리한다.

APP-14는 서버 기반 데이터 구조를 정리했고, APP-11은 모바일 UX 점검 기준을 정리했다. APP-12는 이 두 문서를 바탕으로 실제 사용자가 어떤 순서로 회사방에 들어오고 일정을 사용하는지 확정한다.

---

## 1. 기본 방향

초기 MVP는 무거운 이메일/소셜 로그인을 쓰지 않고, 회사방 + 직원별 초대코드 + PIN 방식으로 진행한다.

```text
회사방 생성
→ 관리자 생성
→ 직원별 초대코드 발급
→ 직원 참여
→ 권한별 일정 확인/등록
→ 퇴사자 비활성화
```

### 핵심 원칙

- 회사방과 일정의 원본은 서버 DB에 둔다.
- localStorage는 캐시와 화면 상태만 맡는다.
- 신규 직원은 기본 viewer 권한으로 시작한다.
- 관리자만 직원 초대, 권한 변경, 비활성화를 할 수 있다.
- 일정 등록/수정은 admin 또는 editor만 가능하다.
- viewer는 일정 확인만 가능하다.
- 퇴사자는 inactive 처리하여 접속을 차단한다.

## 2. 사용자 역할

| 역할 | 영문값 | 주요 권한 |
|---|---|---|
| 관리자 | admin | 회사방 관리, 직원 초대, 권한 변경, 비활성화, 일정 생성/수정/삭제 |
| 쓰기 가능 직원 | editor | 일정 확인, 일정 생성/수정 |
| 읽기 직원 | viewer | 일정 확인만 가능 |
| 비활성화 직원 | inactive | 접근 차단 |

### 권한 기본값

신규 초대 직원은 기본 viewer로 시작한다. 일정 작성이 필요한 직원만 관리자가 editor로 변경한다.

---

## 3. 관리자 최초 흐름

### 3.1 회사방 생성

1. 관리자가 앱에 접속한다.
2. 회사방 생성 버튼을 누른다.
3. 회사명 또는 회사방 이름을 입력한다.
4. 서버가 company_id를 생성한다.
5. 생성한 사용자가 admin 멤버로 등록된다.
6. 앱은 회사방 관리 화면으로 이동한다.

### 3.2 관리자 화면에서 보여야 할 것

- 회사방 이름
- 현재 관리자 이름
- 직원 초대 버튼
- 구성원 목록
- 권한 변경 버튼
- 비활성화 버튼
- 일정 관리로 이동하는 버튼

---

## 4. 직원 초대 흐름

### 4.1 초대코드 발급

1. 관리자가 직원 초대 버튼을 누른다.
2. 직원 표시 이름을 입력한다.
3. 기본 권한은 viewer로 설정된다.
4. 서버가 직원별 초대코드와 PIN을 생성한다.
5. 관리자는 초대코드와 PIN을 직원에게 전달한다.

### 4.2 초대코드 표시 기준

```text
초대코드: SHJJ-A1B2C3
PIN: 123456
권한: 읽기
상태: 사용 전
```

### 4.3 초대코드 상태

| 상태 | 의미 |
|---|---|
| active | 아직 사용 가능 |
| used | 이미 사용됨 |
| revoked | 관리자가 취소 |
| expired | 유효기간 만료 |

---

## 5. 직원 참여 흐름

1. 직원이 앱을 연다.
2. 회사방 참여 화면에서 초대코드를 입력한다.
3. PIN을 입력한다.
4. 서버가 초대코드, PIN, 상태를 검증한다.
5. 검증 성공 시 company_members에 직원이 등록된다.
6. 앱은 해당 회사방 일정 화면으로 이동한다.
7. 직원 권한에 따라 버튼 노출이 달라진다.

### 실패 시 메시지

| 상황 | 메시지 예시 |
|---|---|
| 코드 없음 | 초대코드를 확인해주세요. |
| PIN 오류 | PIN 번호가 맞지 않습니다. |
| 취소된 코드 | 사용할 수 없는 초대코드입니다. 관리자에게 문의하세요. |
| 비활성화 사용자 | 접근이 제한되었습니다. 관리자에게 문의하세요. |

---

## 6. 권한별 화면 흐름

### 6.1 admin

관리자는 다음 항목을 볼 수 있다.

- 오늘 일정
- 월별 일정
- 일정 등록 버튼
- 일정 수정/삭제 버튼
- 구성원 관리
- 직원 초대
- 권한 변경
- 비활성화/복구

### 6.2 editor

editor는 다음 항목을 볼 수 있다.

- 오늘 일정
- 월별 일정
- 일정 등록 버튼
- 본인이 작성한 일정 수정
- 전체 일정 확인

초기 MVP에서는 editor의 삭제 권한은 제한하거나 관리자 승인 대상으로 둘 수 있다.

### 6.3 viewer

viewer는 다음 항목만 볼 수 있다.

- 오늘 일정
- 월별 일정
- 일정 상세 확인

viewer에게는 일정 등록 버튼을 보여주지 않는다. 프론트에서 숨기는 것뿐 아니라 서버에서도 등록 요청을 거부해야 한다.

---

## 7. 일정 등록 흐름

### 7.1 일정 등록 가능 조건

- member status가 active여야 한다.
- role이 admin 또는 editor여야 한다.
- company_id가 현재 회사방과 일치해야 한다.

### 7.2 일정 등록 단계

1. 일정 등록 버튼 클릭
2. 제목 입력
3. 날짜/시간 입력
4. 설명 또는 메모 입력
5. 저장 클릭
6. 서버 권한 검증
7. company_schedules에 저장
8. 일정 목록 새로고침

### 7.3 일정 필수값

| 항목 | 필수 여부 |
|---|---|
| 제목 | 필수 |
| 시작일 | 필수 |
| 종료일 | 선택 또는 자동 |
| 설명 | 선택 |
| 작성자 | 서버에서 자동 입력 |
| 회사방 ID | 서버에서 자동 입력 |

---

## 8. 일정 수정/삭제 흐름

### 수정

- admin은 모든 일정 수정 가능
- editor는 본인이 작성한 일정 수정 가능을 기본안으로 한다.
- 향후 필요하면 editor 전체 수정 가능 옵션을 추가한다.

### 삭제

초기 MVP에서는 실제 삭제보다 status를 deleted로 바꾸는 소프트 삭제를 기본으로 한다.

| 역할 | 삭제 권한 |
|---|---|
| admin | 가능 |
| editor | MVP에서는 제한 권장 |
| viewer | 불가 |

---

## 9. 퇴사자 비활성화 흐름

1. 관리자가 구성원 관리 화면을 연다.
2. 해당 직원의 비활성화 버튼을 누른다.
3. 서버가 company_members.status를 inactive로 변경한다.
4. 관련 초대코드는 revoked 처리한다.
5. 해당 직원이 앱 접속 시 서버 상태를 확인한다.
6. inactive이면 localStorage 멤버십을 제거한다.
7. 접근 제한 안내를 표시한다.

### 중요한 원칙

비활성화는 프론트 UI만으로 처리하면 안 된다. 서버에서 반드시 status를 확인하고 차단해야 한다.

---

## 10. 기기 변경/다중 기기 흐름

초기 MVP에서는 같은 초대코드를 한 번 사용하면 used 상태가 된다. 다만 직원이 다른 기기에서 접속해야 하는 상황이 있다.

### 선택 가능한 방식

| 방식 | 장점 | 단점 | 판단 |
|---|---|---|---|
| 초대코드 1회용 | 보안 좋음 | 기기 변경 불편 | 장기 기본안 |
| 관리자 재발급 | 통제 가능 | 관리 작업 필요 | MVP 적합 |
| 멤버별 재로그인 코드 | 편리 | 추가 설계 필요 | 2단계 |

### MVP 판단

초기에는 관리자 재발급 방식이 가장 단순하고 안전하다.

## 11. 모바일 UX 흐름

APP-11 기준에 따라 모바일에서는 다음 순서를 유지한다.

```text
오늘날씨
→ 오늘 행동 가이드
→ 법령 브리프
→ 오늘일정 / 회사일정
→ 회사방/초대코드 관리
```

### 일정 카드 기준

- 접힘 상태에서도 일정이 있는지 알 수 있어야 한다.
- 펼치면 오늘 일정과 월별 미리보기가 바로 보여야 한다.
- 등록 버튼은 권한이 있는 사용자에게만 보여야 한다.
- viewer에게는 읽기 전용 상태를 명확히 보여야 한다.

### 1단계: 흐름 고정

- 관리자/직원/권한 흐름 확정

- 회사방 참여 화면 정리

### 4단계: 검수

- preview-main에서 아이폰 확인

## 16. 최종 판단

APP-12의 최종 방향은 다음이다.

```text
관리자가 회사방을 만든다.
관리자가 직원별 초대코드 + PIN을 발급한다.
직원은 초대코드 + PIN으로 회사방에 참여한다.
신규 직원은 viewer로 시작한다.
관리자가 필요한 직원만 editor로 승격한다.
admin/editor만 일정을 등록한다.
viewer는 일정을 확인만 한다.
퇴사자는 inactive로 차단한다.
모든 원본 데이터는 서버 DB에 저장한다.
```

이 흐름이 확정되면 다음 구현 작업은 Supabase 테이블과 RPC를 실제 코드에 연결하는 것이다.
